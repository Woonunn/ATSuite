## 来源与清洗

七个发布资产共 3,218,886,136 字节，发布方 SHA256 全部通过；606 个 gzip JSONL shard 的大小/Session 数与官方 manifest 一致。release ID 400522856，tag Commit `207bed67dd10090b28ad4f745b2cfd41a11aace4`，文档 Commit `215becdacba1ce682c7368642ce97d5a332de7a6`；精确锁见 `data/copilot_source.lock.json`。

## 原速 Docker 验收

使用已有镜像 `sha256:c11ba32bbcd3cd398de643553593ac127833419743e3e5cb5eeb992a34796588`，每例 2 CPU / 2 GiB，网络关闭，不挂载 .env 或云凭据。各窗只跑预定的**前 120 秒切片**，保留切片的原始间隔、初始及末尾空闲。三个切片并行是三次独立验证，不合称一条生产流量。CPU Harness 为固定 PBKDF2 工作，不是 DataSciBench/LLM 执行轨迹。

| 窗口 | 计划/实际完成请求 | 提交误差 P99 ms | 提交误差最大 ms | Harness 开始误差 P99 ms | 峰值队列 | 提交缺失率 / 失败拒绝率 |
| --- | --- | --- | --- | --- | --- | --- |
| low | 7 | 0.934 | 0.938 | 1.427 | 2 | 0 / 0 |
| typical | 31 | 1.391 | 1.415 | 30.925 | 5 | 0 / 0 |
| high | 81 | 1.572 | 1.623 | 132.300 | 9 | 0 / 0 |

共 119 个请求，全部实际提交并成功完成；每个 ID 恰有一次开始/终态，计划纳秒间隔与原始切片完全相同。计时基于单调时钟，另存 UTC。高流量 Harness 的启动迟延明显高于提交误差，来自实际并发限制/排队，未混成调度误差或填零。正常场景未发生拒绝；队满、执行异常、中断和积压排空路径由合成控制流测试验证，不伪称为生产失败样本。

首次定时器实现的执行记录保留在 `results/phase3/timing-v1`，同一切片没有丢失，但长空闲后最大提交迟延约 40.50 ms。改为绝对 deadline 加最长 100 ms 的分段等待后，`timing-v2` 的最大提交迟延为 1.623 ms。没有改源时间、切片或执行负载；两次证据均保留。

最终 **91/91 测试通过**，包括已有 82 项兼容性检查，以及首次用户/跨分区去重/不提升后续 Turn、纳秒精度、源资产绑定、tar 路径安全、open-loop、不丢账、队列满/异常、显式缩放和中断清理。原始解析器源码快照保存为 extractor_used.py；最终补强的分区到发布资产绑定检查还独立复核了全部七个真实归档，未改变已生成到达内容。
